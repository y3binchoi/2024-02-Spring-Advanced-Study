# 9.3 애플리케이션 아키텍처

## 9.3.1 계층형 아키텍처

> 지금까지 관심, 책임, 성격, 변하는 이유와 방식이 서로 다른 것을 분리함으로써 분리된 각 요소의 응집도를 높이고 서로의 결합도를 낮췄다. 성격이 다른 모듈이 강하게 결합되어 있으면 그와 상관 없는 요소도 영향을 받아 불필요한 부분까지 변경하게 된다. 그래서 인터페이스와 같은 유연한 경계를 만들어두고 분리하거나 모아주는 작업을 수행한다. 

### 아키텍처와 SoC

오브젝트 레벨에서 관계를 맺어주는 제 3의 존재, DI 컨테이너를 둠으로써 오브젝트끼리 직접 관계를 맺지 않고 인터페이스로 유연하게 결합할 수 있게 했다.

오브젝트를 하나의 모듈 단위라고 생각해보면 이런 원리를 아키텍처 레벨에서도 동일하게 적용할 수 있다.  

또한 더 작은 단위로 하나의 메소드 레벨에서도 같은 방식의 접근이 가능하다. 

애플리케이션의 오브젝트들을 유사한 성격을 띈 그룹으로 나눠보자:
- DAO들을 하나의 단위로 생각해본다. 어떤 DAO든 비슷한 성격을 띠고 유사한 방식으로 관계를 맺는다. 
- 어떤 비즈니스 서비스 오브젝트도 묶을 수 있겠다. 서비스 오브젝트들은 특정 기술과 환경에 종속되지 않으면서 도메인의 업무와 밀접한 관련을 갖고 있는 POJO로 만들어진다.
- 웹을 처리하는 오브젝트도 독자적인 성격으로 분류할 수 있다. 서블릿 컨테이너로부터 받은 사용자 요청 정보를 해석하여 그것을 POJO 기반의 서비스 오브젝트에 전달해주고, 결과를 받아서 다시 웹 사용자 인터페이스에 표시 가능한 형태로 변환해주는 일을 한다. 

이렇게 분리했을 때 장점:
- 분리된 각 오브젝트는 독자적으로 개발,테스트가 가능해서 개발~변경 작업이 빨라진다.
- 구현 방법이나 세부 로직은 서로 영향을 주고 받지 않아 변경이 쉽다. 
- 전체의 기능,구조를 이해하기 쉽다. 

이렇게 책임과 성격이 다른 것을 크게 그룹으로 만들어 분리하는 것을 `계층형 아키텍처`라고 부른다. 또는 `multi tier architecture`라고도 한다. 

보통 웹 기반 엔터프라이즈 애플리케이션은 일반적으로 세 개의 계층을 갖는다. 이를 3계층(3-tier or 3-layer)애플리케이션이라고도 한다. 

### 3계층 아키텍처와 수직 계층

3계층 아키텍처:
- 데이터 액세스 계층: 백엔드의 DB나 레거시 시스템과 연동하는 인터페이스 역할
- 서비스 계층: 비즈니스 로직을 담음
- 프레젠테이션 계층: 주로 웹 기반의 UI를 만들어내고 그 흐름을 관리

#### 데이터 엑세스 계층 
DAO 계층이라고도 불린다. 보편적으로 DAO 패턴을 사용하기 때문이다. 이게 주된 책임이다. 
또한 DB 외에도 ERP, 레거시 시스템, 메인프레임 등에 접근하기도 해서 `Enterprise Information System` 계층이라고도 한다. 이걸 따로 떼서 기반<upper>infrastructure</upper> 계층으로 분류하기도 한다.

데이터 엑세스 계층의 사용 기술에 따른 계층 분류를 할 수 있다. 이건 추상화 수준에 따른 구분이기에 수직적 계층이라고도 한다. 

수직적 구조에서는 새로운 계층 추가가 애플리케에션 코드에 큰 영향을 주기 때문에 최대한 유지할 수 있도록 코드를 작성하는 것이 중요하다. 

#### 서비스 계층
구조가 가장 단순하며 이상적인 POJO로 작성된다. 

DAO 계층을 호출하고 이를 활용하는 오브젝트로 이루어진다. 

이외에도 웹 서비스와 같은 원격 호출을 통해 정보를 가져오거나, 메일 또는 메시징 서비스를 이용할 경우가 있다. 이런 기반 서비스는 3계층 어디서나 접근 가능하도록 만들수도 있고, 반드시 서비스 계층을 통해 사용되도록 제한할 수도 있다. 

특별한 경우가 아니라면 수직 계층구조를 가질 필요가 없다. 기술 API를 직접 다루는 코드가 아니기 때문이다. 

서비스 계층이 서비스 계층의 오브젝트를 호출하는 경우를 자세히 봐보자. 
일반적으로는 서비스 계층이 필요에 따라 기반 서비스 계층 API를 호출해서 이용한다.
하지만 반대로 서비스 계층의 코드를 기반 서비스 계층에서 실행시키는 경우가 있다.

스케쥴링:
- 미리 정해진 시간에 특정 서비스 계층의 로직을 동작하게 만드는 백그라운드 서비스 

원칙적으론 서비스 계층 코드가 기반 서비스 계층의 구현에 종속되선 안된다:
- 기반 서비스 API로만 접근하게 만들어 특정 구현과 기술에 대한 종속성을 제거하거나
- AOP를 통해 서비스 계층 코드를 침법하지 않고 부가기능을 추가해야 한다 

#### 프레젠테이션 계층
가장 복잡하다. 일단 엔터프라이즈 애플리케이션의 프레젠테이션 계층은 클라이언트 종류와 상관 없이 HTTP 프로토콜을 사용하는 서블릿이 바탕이 된다. 

다른 계층과 달리 클라이언트까지 그 범위를 확장할 수 있다. 
초기 클라이언트 모델은 단순히 HTML을 사람이 볼 수 있게 그려주고, 폼을 통해 입력받은 값을 전달하는 것이었다. 
모든 프레젠테이션 로직은 서버의 프레젠테이션 계층의 컴포넌트에서 처리된다. 화변 흐름, 사용자 입력 값에 대한 검증, 서비스 계층 호출, 전달되는 값 포맷 변화, 뷰view라고 불리는 화면을 어떻게 그릴지 까지 모두 서버에서 처리됐다. 
하지만 최근에는 프레젠테이션 로직이 클라이언트로 이동하는 추세다. RIA 기술이나 SOFEA 아키텍처가 대표적 예이다.


### 계층형 아키텍처 설계 원칙

역시 객체지향 설계 원칙을 적용한다. 각 계층은 응집도가 높으면서 다른 계층과는 낮은 결합도를 유지하도록 설계한다. 자신의 역할과 기술에만 충실한 계층을 마늗ㄹ며 각 계층 사이의 결합도도 낮아진다. 

데이터 엑세스 계층 예시 
```java
public ResultSet findUserByName(String name) throws SQLException;
```
나쁜 이유:

```java
public List<User> findUserByName(String name) throws DataAccessException;
```
좋은 이유

프레젠테이션 계층 예시
```text
서블릿의 HttpServletRequest나 HttpServletResponse, HttpSession 같은 타입을 서비스 계층 인터페이스 메소드의 파라미터 타입으로 사용
```
나쁜 이유:

```text
계층 경계를 넘어갈 때 반드시 특정 계층에 종속되지 않는 오브젝트 형태로 변환
```
좋은 이유:

인터페이스 하나 더 만드는게 번거롭다고 그냥 클래스로 만들지 말자. 인터페이스를 사용한다는 건 각 계층의 경계를 넘어 들어오는 요청을 명확히 정의하는 것이다. 

인터페이스에 클래스의 모든 public 메소드를 담아서도 안된다. 
한번 정의되어 다른 계층에서 사용하기 시작하면 변경이 매우 어려워지고 비용이 많이 들게 된다. 다른 계층에서 꼭 필요한 메소드만 노출하자. 

스프링의 DI는 기본적으로 오브젝트 사이의 관계를 다룬다. 모든 경계엔 오브젝트가 존재하고 그 사이 관계도 스프링 DI가 관여한다고 볼 수 있따. 하지만 DI는 계층을 구분해주지 않기 때문에 빈 사이 의존관계를 만들 때 주의해야 한다. 

## 9.3.2 애플레케이션 정보 아키텍처

엔터프라이즈 시스템:
- 동시에 많은 작업을 빠르게 수행하는게 목적
- 사용자 요청을 처리하는 동안만 간단한 사용자 작업 상태를 유지함
- 주요 상태 정보는 클라이언트/백엔드 시스템에 분산되어 보관됨
- 비교적 장기간 보관될 상태정보는 주로 DB나 메인프레임 같은 EIS 백엔드 시스템에 저장
- 하나의 업무 작업이 여러 번의 요청과 페이지에 걸쳐 일어나는 경우, 유지되어야 하는 임시 상태정보는 클라이언트나 서버의 사용자별 세션 메모리에 저장

애플레케이션을 사이에 두고 흘러다니는 정보르 어떤 식으로 다룰까:
- 정보를 단순히 데이터로 다루는 경우
- 오브젝트로 다루는 경우 

### 데이터 중심 아키텍처

특징:
- 흐르는 정보를 단순히 값 또는 값을 담기 위한 목적의 오브젝트 형태로 취급한다.
- 비즈니스 로직이 DB 내부의 저장프로시저나 SQL에 담겨 있는 경우가 많다.
- 보통 DB에서 돌려주는 내용을 그대로 맵이나 단순 결과 저장용 오브젝트에 넣어서 전달한다.  DB 결과 값은 가공은 할수도, 안할수도 있다. 

### DB/SQL 중심의 로직 구현 방식

특징:
- 하나의 업무 트랜잭션에 모든 계층의 코드가 종속되는 경향을 보임. 
	- 사용자 조회라는 단위 업무가 정해지면, 각 계층에 그 업무를 위해서만 존재하는 코드가 만들어짐. 
- SQL이 화면이 어떤 식으로 출력될 지 알고 있다.
- 이 경우 서비스 계층이 할 일이 없다. 프레젠테이션 계층의 JSP 뷰가 DAO의 SQL이 어떤 필드를 어떤 포맷으로 전달할 지 알고 있기 때문.
- 대용량 데이터를 빠르게 처리하기 위해 PL/SQL 같은 저장 프로시저 형태로 일부 로직을 만들기도 한다.
- 자바 기술이 발전하기 이전의 엔터프라이즈 시스템이 이런 구조였다. 3~2계층 구조.

단점: 
- 수정,추가 사항이 전파된다. DB 테이블 -> 엔트리,프로퍼티 수정,추가 -> 맵,오브젝트 수정,추가 -> 뷰 수정,추가 
- 개발 초기엔 쉬울지 모르나 객체 지향 원칙을 지키지 않아 변화에 취약하고 SQL이나 저장 프로시저에 담긴 로직을 테스트하기 쉽지 않다. 

### 거대한 서비스 계층 방식

특징: 
- DB에서 가져온 데이터가 애플리케이션을 흘러다니는 정보의 중심이 되는 아키텍처.
- 하지만 DB에 많은 로직을 두는 개발을 피하면서 애플리케이션 코드의 비중을 높인다.
- DB에 부하가 걸리지 않도록 저장 프로시저의 사용을 자제하고, 복잡한 SQL을 쓰는 대신에 주요 로직을 서비스 계층 코드에서 처리하게 만든다.
- 비즈니스 로직을 DB나 SQL에 담는 경우 항상 최종 결과만 DAO에서 서비스 계층으로 전달된다. 
- 반면에 거대 서비스 계층 방식에서는 DAO에 좀 더 단순한 결과를 돌려준다. DAO가 돌려준 정보를 분석,가공하면서 비즈니스 로직을 적용하는 것이 서비스 계층 코드의 책임이 된다. 
- 업무 트랜잭션 단위로 서비스 계층의 메소드가 만들어질 가능성이 높다. 그러다 보면 하나의 메소드가 매우 거대해질 수 있다. 

장점:
- 애플리케이션 코드의 비중이 커져 구조가 단순해지고 객체지향 개발의 장점을 살릴 기회가 생긴다. 
- DAO와 SQL이 상대적으로 단순해지고, 서비스 계층 코드에서의 재사용성이 높아진다. 

단점:
- 데이터 엑세스 계층의 SQL이 서비스 계층의 필요에 따라 만들어지기 쉽다. 이로 인해 여전히 계층 간 결합도가 크다. 


## 9.3.3 오브젝트 중심 아키텍처

특징:
- 데이터 중심 아키텍처와 가장 다른 점은 도메인 모델을 반영하는 오브젝트 구조를 만들어 두고 그것을 각 계층 사이에서 정보를 전송하는 데 사용한다는 것이다. 
- 객체지향 분석과 모델링의 결과로 나오는 도메인 모델을 오브젝트 모델로 활용한다. 
- 대개의 도메인 모델은 DB 엔티티 설계에도 반영되어 둘이 유사한 형태일 가능성이 높다. 물론 DB엔 없고 비즈니스 로직에만 존재하는 모델도 있을 수 있다. 

### 데이터와 오브젝트 방식 비교

조건: 


요구 사항: 
조건에 맞는 모든 카테고리와 상품 정보를 가져와 화면에 출력

데이터 중심:
- SQL과 DB 관점에서 생각
- 두 개의 정보를 조합해서 가져오려면 `JOIN`을 아용해 2차원 구조의 정보를 만든다
- 다음을 실행하고 결과를 맵으로 받는다. 배열도 가능한데 필드 이름을 일일이 기억하기 귀찮으니까. 
```mysql
select c.categoryid, c.description, p.productid, p.name, p.price 
from product p
join category c on p.categoryid = c.categoryid
```
- 결국 DAO가 만드는 SQL의 결과에 모든 계층의 코드가 의존하게 된다. 

오브젝트 방식:
- 애플리케이션에서 사용되는 정보가 도메인 모델의 구조를 반영해서 만들어진 오브젝트 안에 담긴다. 
- 따라서 도메인 모델이 반영된 도메인 오브젝트도 전 계층에서 일관된 구조를 유지하며 사용될 수 있다. 
- SQL이나 웹 페이지 출력 포맷, 입력 폼 등에 종속되지 않는 일관된 형식의 애플리케이션 정보를 다룬다. 

### 오브젝트 방식의 문제점

- 최적화된 SQL을 매번 만들어 사용하는 경우에 비해 성능 면에서 손해를 감수해야 한다. DAO가 비즈니스 로직에서의 사용 방식을 알지 못해 도메인 오브젝트의 모든 필드 값을 다 채워서 전달하는 경우가 대부분이기 때문. 
- 오브젝트 관계 때문에 단순히 Product 정보만 필요한 경우에도 Category 오브젝트도 함께 담겨 나오는 낭비가 발생할 수 있다. 
- 물론 Product 정보를 가져올 때 Category가 필요한 경우/그렇지 않은 경우를 구분해서 DAO를 만들 수도 있다. 하지만 문제는 DAO에서 Product만 가져오면 category 필드에 null이 들어가고 이는 `NullPointException`의 위험 요소가 된다. 

해결:
- 지연 로딩<upper>lazy loading</upper>방식은 일단 최소한의 오브젝트 정보만 읽어두고 관계 하고 있는 오브젝트가 필요한 상황에 다이내믹하게 DB에서 읽어온다. 코드 작성 시에는 그냥 처음부터 모든 오브젝트 정보가 다 제공된다고 생각하고 짜면 된다. 
- 필드가 너무 많은 테이블의 경우, 그중에서 자주 사용되는 것을 골라내 별도의 오브젝트로 정의하고 필요에 따라 구분해서 사용할 수 있다. 약한 계층 간의 결합이 발생할 수 있다. 
- 가장 이상적인 방법은 JPA, JDO, 하이버네이트, TopLinK 같은 오브젝트-RDB 매핑<upper>ORM</upper> 기술을 사용하는 것이다. 이런 데이터 엑세스 기술은 기본적으로 지연 로딩 등의 기술을 제공해서 번거로운 코드를 만들지 않고도 도메인의 오브젝트 생성을 최적화할 수 있다. 
- 또한, SQL 결과로 도메인 오브젝트를 만들고 값을 채우는 DAO 코드를 만들지 않아도 된다. 

#### 빈약한 오브젝트 방식
- 도메인 오브젝트가 데이터를 저장해두는 것 외에 아무 기능이 없다. 
-- 데이터중심아키텍처>거대서비스계층구조 와 비슷하다. 

### 풍성한 도메인 오브젝트 방식
-  `rich domain object` 또는 영리한  도메인 오브젝트`smart domain object` 방식으로 부른다. 
-  객체지향적으로 개선한 것. 
- 어떤 비즈니스 로직은 특정 도메인 오브젝트나 그 관련 오브젝트가 가진 정보와 깊은 관계가 있다. 이런 로직을 서비스 계층의 코드가 아니라 도메인 오브젝트에 넣어주고, 서비스 계층의 비즈니스 로직에서 재사용하게 만드는 것이다. 

서비스 계층에 대하여:
- 도메인 오브젝트에 비즈니스 로직을 넣는다고 서비스 계층 오브젝트가 필요 없어지는 것은 아니다. 도메인 오브젝트 안에 메소드로 들어가는 로직은 대부분 해당 오브젝트나, 긴밀한 연관관계를 맺고 있는 관련 오브젝트의 정보와 기능만을 활용한다. 이보다 복잡한 로직은 서비스 계층 오브젝트에 두는 것이 옳다. 
- 도메인 오브젝트는 직접 데이터 엑세스 계층이나 기반 계층 등 다른 계층의 오브젝트로 접근할 수 없기 때문에 서비스 계층이 필요하다. 
- 도메인 오브젝트는 DI 받을 수 없다. 스프링이 관리하는 오브젝트가 아니기 때문이다. 즉, 빈이 아니다. 
- 도메인 오브젝트는 애플리케이션 코드 어디에서든 필요할 때마다 새롭게 만들어진다. 따라서 빈으로 등록하면 안되고 DI를 받을 수 없게 된다.
- 그래서 수식 계산이나 조건에 따른 데이터 변경 또는 자신이 가진 정보에 대한 분석 같이 자기 자신에 국한된 로직은 추가할 수 있지만, 그 결과를 DB에 저장하거나, 메일로 발송하거나, DB를 검색해서 원하는 정보를 가져와 활용하는 작업은 불가능하다. 
- 그래서 DAO와 기반계층 오브젝트를 DI받아 사용할 수 있는 서비스 계층 코드가 필요한 것.

(그림)

- 도메인 모델링을 충실히 해놓지 않았따면 차라리 데이터 구조만 오브젝트 방식으로 정의해놓은 빈약한 도메인 오브젝트 방식이 혼란을 피하면서 더 쉽게 접근하는 대안이 될 수 있다. 하지만 코드 규모가 커질수록 혼란스러워질 것. 

### 도메인 계층 방식

- 지금까지 도메인 오브젝트에 담는 비즈니스 로직은 DA 계층에서 가져온 내부 데이터 분석, 조건에 따른 오브젝트 정보 변경,생성 등의 작업처럼 한계가 있었다. 이렇게 변경된 정보를 다시 DB 등에 반영하기 위해 결국 서비스 오브젝트에서 부가적인 작업이 필요했다.

> 도메인 오브젝트가 스스로 필요한 정보를 DAO를 통해 가져오고, 생성이나 변경이 일어났을 때 직접 DAO에게 변경사항을 반영해달라고 요청할 순 없을까? DAO 외에도 다양한 기반계층 서비스를 이용하도록 할 방법은 없나? 만약 도메인 오브젝트가 기존 3계층 오브젝트를 DI 받아서 직접 이용할 수 있게 되면 어떤 일이 일어날까?

도메인 계층 방식이란:
- 도메인 계층의 역할이 커져 기존 3계층과 같은 레벨로 격상되어 하나의 계층을 이루는 방식.
- 하나의 독립적인 계층으로 서비스 계층과 데이터 엑세스 계층 사이에 존재.

특징:
1. 도메인에 종속적인 비즈니스 로직의 처리가 서비스 계층이 아니라 도메인 계층 오브젝트 안에서 일어남.
	- 일단 도메인 계층에 들어가면 서비스 계층의 도움 없이도 비즈니스 로직의 대부분의 작업을 수행할 수 있음.
2. 도메인 오브젝트가 기존 데이터 엑세스 계층이나 기반 계층의 기능을 직접 활용할 수 있다. 여전히 도메인 오브젝트는 빈이 아니지만, 스프링이 관리하는 오브젝트가 아니어도 DI를 적용할 방법이 있다. 이를 위해선 AOP가 필요하다.

도메인 오브젝트에 AOP 적용:
- 일단 스프링 AOP는 부가기능을 추가할 수 있는 위치가 메소드 호출 과정으로 한정되어 있다. 
- AOP의 적용 대상도 스프링의 빈 오브젝트뿐이다.
- 하지만 AspectJ AOP를 사용하면 클래스의 생성자가 호출되면서 오브젝트가 만들어지는 시점에 조인 포인트를 사용할 수 있고, 스프링 빈이 아닌 일반 오브젝트에도 AOP 부가기능을 적용할 수 있다. 
- 도메인 오브젝트가 생성되는 시점에 오브젝트의 수정자 메소드나 DI용 애노테이션을 참고해 DI 가능한 대상을 스프링 컨테이너에서 찾아 DI 해주는 기능을 추가해준다. 
- 이 방법으로 도메인 오브젝트가 만들어질 때 빈을 DI 받아서 도메인 오브젝트가 데이터 엑세스 계층이나 기반 계층의 오브젝트를 이용할 수 있게 된다. 물론 자신과 관련된 오브젝트에 대한 작업으로 한정해야겠지만.

그럼 서비스 계층이 필요 없나?
- 그렇진 않다.
- 여러 도메인 오브젝트의 기능을 조합하여 복잡한 작업을 처리하거나
- 특정 도메인 오브젝트에 담길 수 없는 작업을 담거나
- 굳이 도메인 계층을 거치지 않고 바로 데이터 엑세스 계층으로부터 정보를 가져와 클라이언트에 제공할 수도 있다. 
- 또한 트랜잭션 경계를 설정하거나 
- 특정 도메인 로직에 포함할 순 없으나 애플리케이션에서 필요로 하는 기반 서비스를 이용하는 작업을 위해서 필요하다. 
- 대신 서비스 계층의 비중과 규모가 훨씬 작아진다. 

도메인 오브젝트를 도메인 계층 밖에서 사용하는 방식:
1. 모든 계층에서 도메인 오브젝트를 사용하는 방식이 있다. 모든 계층에서 직접 도메인 오브젝트를 전달받아 사용할 수 있게 하면 도메인 로직은 도메인 오브젝트에서 진행하고, 그 결과를 DB에 반영할 때나 화면에 출력하거나 페이지 이동을 위한 정보로 활용하기 위해 프레젠테이션 계층에서 참조할 때도 도메인 오브젝트를 이용할 수 있다. 

하지만 도메인 오브젝트의 메소드는 단순히 값을 조작, 분석, 변환하는게 아니라 중요한 도메인/비즈니스 로직을 담당한다. 띠라서 함부로 이를 프레젠테이션 계층이나 뷰에서 활용할 경우 중요한 비즈니스 로직을 담은 메소드를 호출하는 문제가 일어날 수 있다. 오브젝트를 넘겨받고 나면 사용에 제약이 없기 때문에 더욱 함부로 조작하거나 실행할 위험이 있다. 

무분별한 메소드 호출을 막기 위한 가장 간단한 방법은 철저한 개발 정책을 만들고 적용하는 것이다. 규정을 어기는 개발자를 막기 위해 코딩 정책을 적용하는 툴을 이용해 검증하거나 AspectJ의 정책/표준 강제화<upper>policy/standards enforcement</upper>를 사용하면 좋다. 간단한 포인트컷 표현식으로 특정 계층의 오브젝트가 사용할 수 있는 메소드 범위를 제한하는 등의 정책 강제화 작업이 가능하다. 

2. 도메인 오브젝트가 도메인 계층을 벗어나지 못하게 하는 방식이 있다. 도메인 계층 밖으로 전달될 땐 별도의 정보 전달용 오브젝트에 도메인 오브젝트의 내용을 복사해 넘긴다. 이런 오브젝트를 DTO<upper>Data Transfer Object</upper>라고 부른다. 반대로 사용자가 등록한 값이나 외부 시스템으로부터 전달받은 정보를 도메인 계층에 전달할 때도 DTO를 이용한다. 

DTO는 기능을 갖지 않아서 안전하고 도메인 오브젝트를 외부로부터 보호한다. 하지만 비슷한 구조의 오브젝트를 또 만들어서 변환해야 한다는 번거로움이 있다. 따라서 AOP 같은 방법을 이용해 자동으로 변환되도록 만들 필요가 있다. 

둘 중 절대적으로 나은 방법은 없다. 번거로운 작업을 최소화 하고 표준 개발 정책을 잘 강제할 수 있다면 전자, 이미 기존에 DTO를 이용한 개발에 익숙하다면 후자가 더 나을 것이다. 

(그림)

도메인 계층은 기존 3계층과 달리 생명주기가 짧다. 도메인 오브젝트는 사용자별 요청에 대해 독립적인 상태를 유지하고 있어야 하기 때문이다. 상태정보를 담고 있기 때문에 여러 스레드가 공유하는 싱글톤이 되어선 안된다. 또한 DAO나 컨트롤러, 또는 스프링 외의 라이브러리를 통해 오브젝트가 만들어지는 경우가 많아 스프링빈으로 등록되기 어렵다. 

이런 제약사항에도 불구하고 도메인 오브젝트를 사용해야 하는 경우는 매우 복잡하고 변경이 잦은 도메인을 가졌을 때다. 도메인의 구조와 로직을 최대한 도메인 계층의 오브젝트에 반영하면 도메인 모델에 변경이 생겨도 오브젝트의 변경이 쉬워진다. 도메인 계층의 응집도가 매우 높기 때문에 DAO나 외부 서비스 오브젝트와 연동할 때 도메인 오브젝트 타입을 유지하면서 목 오브젝트 등을 이용해 단위 테스트를 만들기 쉽다. 반면에 그렇게 복잡하지 않다면 과도한 부담이 될 수 있다. 

#### DTO와 리포트 쿼리

오브젝트 중심 아키텍처는 애플리케이션 내의 모든 정보를 항상 도메인 오브젝트에 담아야 할까? 
- 그렇지 않다. 정보전달을 목적으로 DTO에 도메인 계층을 벗어나는 정보를 담아 사용할 수 있다. 

리포트 쿼리:
- DB 쿼리의 실행 결과를 담는 것. 리포트를 출력하기 위해 생성하는 쿼리라는 의미다. 보통은 종합 분석 리포트처럼 여러 테이블에 걸쳐 존재하는 자료를 종합/분석/통계 결과를 생성하는 쿼리를 의미한다. 따라서 이것만을 위해 도메인 오브젝트를 만들 순 없고 DB 쿼리 실행 결과를 담을만한 DTO라 불리는 단순한 자바빈이나 키와 값 쌍을 갖는 맵에 담아서 전달해야 한다. 
- 최종 결과를 쿼리 이후에 자바 코드로 다시 분석,가공하거나 웹 서비스 등 시스템과 자료를 주고받을 때 전송 규약에 맞춰 도메인 오브젝트의 정보를 가공할 때도 DTO나 맵을 이용해 적절한 형식으로 변경한다. 


## 9.3.4 스프링 애플리케이션을 위한 아키텍처 설계 

아키텍처는 역할 분리, 정보를 다루는 방법, 기술 조합, 업무조건, 시스템 환경 등 많은 변수에 의해 계층구조가 나눠지고 애플리케이션 정보를 어떻게 다룰지 결정하게 된다.  

### 계층형 아키텍처

3계층 구조는 스프링 엔터프라이즈 애플리케이션에서 가장 많이 사용되는 구조다. 그만큼 스프링 주요 모듈과 기술이 3계층 구조에 적합하도록 설계되어 있다. 단, 3계층은 논리적/개념적 구분이며 오브젝트 단위로 딱 끊어지지 않으므로 얼마든지 간소화/확장할 여지를 남겨두어야 한다. 

스프링을 처음 도입한다면 가장 전통적인 서버 기반의 3계층 구조에 먼저 익숙해지는 것이 좋다. 
- 프레젠테이션 계층: SpringMVC
- 서비스 계층: POJO + 트랜잭션 AOP
- 데이터 액세스 계층: JDBC를 비롯한 JPA, 하이버네이트, JDO...

### 정보 전송 아키텍처

일단 빈약한 도메인 오브젝트 방식으로 시작한다. 스프링으 ㅣ기본 기술에 가장 잘 들어맞고 쉽게 적용해볼 수 있는 아키텍처이기 때문이다. 

DB와 SQL에 많은 비즈니스 로직을 담고 있는 레거시 시스템을 스프링으로 전환하는 경우라면, 일단 데이터 중심 아키텍처로 시작해본다.

### 상태 관리와 빈 스코프

아키텍처 설계에서 한 가지 더 신경써야 할 것은 `상태 관리`다. 로그인 세션 관리, 위저드 기능등 애플리케이션은 하나의 HTTP 요청의 범위를 넘어 유지해야 하는 상태정보가 많다. 

엔터프라이즈 애플리케이션 하나는 동시에 수많은 사용자의 요청을 처리하기 위해 매번 간단한 요청을 받아서 그 결과를 돌려주는 방식으로 동작한다. 서버 기반의 애플리케이션은 상태를 갖지 않는다. 
이를 위해 웹 클라이언트라면 URL, 파라미터, 폼 히들 필드, 쿠키 등으로 정보나 서버에 저장된 상태정보의 키 값을 저장한다. 중요한 상태 정보는 파일 시스템, 데이터 그리드, DB 등에 저장되기도 한다. 또는 제약이 있긴 하지만 HTTP 세션과 같은 서블릿 컨테이너가 제공하는 저장공간을 활용하기도.

스프링에서는 싱글톤 외에도 다른 스코프를 갖는 빈을 만들 수 있다. 빈 스코프를 활용해서  빈이면서 사용자별/단위 작업별로 독립적으로 생성되고 유지되는 오브젝트를 만들어 상태를 저장하고 DI로 서비스 빈이 사용 가능하게 만들 수 있다. 

### 서드파티 프레임워크, 라이브러리 적용

스프링은 기본적으 J2EE 1.4, Java## 5.0을 지원하며 거의 대부분의 자바 표준 기술과 함께 사용할 수 있다. 표준 기술 이외에도 오픈소스 프레임워크나 라이브러리, 상용 제품도 함께 사용할 수 있는데 이때 일단 스프링이 그 기술을 공식적으로 지원하는지 확인해야 한다. 

### 스프링이 지원하는 기술이란?

1. 해당 기술을 스프링 DI 패턴을 따라 사용할 수 있다:
프레임워크나 라이브러리의 핵심 클래스를 빈으로 등록하게 해준다고 생각해도 좋다. 코드를 이용해 초기화해야 하는 기능을 빈으로 등록하는 것만으로 바로 사용할 수 있다. 

스프링 외의 기술을 접목할 땐 가장 먼저 스프링의 빈으로 등록하고 DI 방식을 통해 사용 가능한지 살펴본다. 빈으로 바로 사용할 수 없으면 팩토리 빈을 도입해야 한다. 

예를 들어 하이버네이트 사용을 위한 SessionFactory를 사용하기 위해 LocalSessionFactoryBean에 적절한 프로퍼티를 빈으로 등록되고 DI 될 수 있게 만든다.

2. 스프링의 서비스 추상화가 적용:
사용기술의 API를 그대로 노출하기 보다 비슷한 기능ㅇ르 제공하는 기술에 대한 일관된 접근 방법을 정의한다. 이를 통해 서드파티 뿐만 아니라 필요에 따라 호환 가능한 기술로의 교체가 쉬워진다. 이는 개발자에게 일관된 방법으로 코드 작성을 해준다.는게 중요하다. 

3. 스프링이 지지하는 프로그래밍 모델을 적용했다:
예를 들어 스프링의 데이터 엑세스 지원 기능은 DAO를 데이터 엑세스 기술에 독립적으로 일관된 예외 계층 구조를 던지도록 한다.  이는 스프링의 데이터 엑세스 예외를 추상화하고, 불필요하게 예외를 처리하는 코드를 피하도록 런타임 위주의 예외를 작성하는 스프링의 개발철학이 뭍어있다. 

4. 템플릿/콜백이 지원된다:
JDBC, JMS, JCA 등 20여개의 기술이 템플릿/콜백을 제공한다. 이 기능을 통해 스프링은 이런 ㅣ술을 간편하게 사용할 수 있는 템플릿/콜백 기능을 제공한다. 

스프링이 어떤 기술을 지원한다는 건 결국 스프링이 지지하는 개발철학과 프로그래밍 모델에 따르면서 해당 기술을 사용할 수 있다는 말이다. 스프링에 새로운 기술을 연동하려면 스프링의 프로그래밍 모델과 개발철학을 따르면서 앞에서 설명한 네 가지 방법을 이용하면 된다. 

정리하자면:
1. 스프링 빈으로 해당 기술의 핵심 오브젝트를 등록한다. 필요에 따라 팩토리 빈을 사용해서 오브젝트 생성, 초기화, 프로퍼티 노출 등을 해준다. 애플리케이션 내의 빈들이 새로운 기술에 대해 빈에 DI 하는 방식으로 접근할 수 있게 만드는 작업이다.

2. 서비스 추상화를 시도할수도 있다. JavaMail처럼 테스트가 매우 까다롭게 설계된 기술이라면 유연성, 테스트 용이성을 위해서 새로운 인터페이스를 추가할 필요가 있다. 

3. 네트워크 접근, 파일 IO같은 실패 가능성이 있는 시도를 한다면 템플릿/콜백 방식 적용을 적극 고려해볼 수 있다. 

4. 때로는 AOP나 예외 전환을 적용할 수도 있다. 보통 외부에서 가져와 사용하는 기술은 내부 구현을 변경하기 쉽지 않다. 이럴 때 AOP로 예외 변환을 시도해볼 수 있다. 특정 예외가 던져졌을 때에 대한 포인트컷을 만들어두고, 어드바이스에서 예외를 추상화된 런타임 예외로 바꿔서 다시 던져주면 된다. 그럼 해당 API를 사용하는 코드를 전혀 손대지 않고도 손쉽게 예외 변환이 가능하다. 

## 9.3.4 정리

- 스프링에 가장 잘어울리는 아키텍처는 오브젝트 중심 아키텍처이다. 
- 역할에 따라 3계층으로 구분할 수 있고 다시 기술의 추상도에 따라 세분화되는 계층형 아키텍처를 사용하는게 좋다. 
- 스프링이 직접 지원하지 않는 서드파티 기술도 스프링 스타일의 접근 방식을 따라 사용할 수 있다.
